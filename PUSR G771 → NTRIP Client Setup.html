Turning a PUSR G771 into an NTRIP client

Streaming RTK/RTCM corrections over a cellular modem's serial port, using Transparent Mode and a hand-built HTTP GET request — no native NTRIP support required.

PUSR G771 / G771-E Transparent mode Centipede RTK caster
Why this works: NTRIP is just an HTTP GET request sent once over a TCP socket, followed by a continuous RTCM binary stream. The G771 has no NTRIP mode built in — but its Identity Package feature can send that one GET request automatically the moment the socket connects, and Transparent mode passes everything after that straight to the serial port untouched.

Set the work mode to Transparent

In the config utility, this is the mode where the modem simply relays bytes between the cellular network and the serial port — no protocol handling of its own.

Point Socket A at the caster

Enable Socket A, set it to TCP, and point it at your NTRIP caster's address and port. Set the link as persistent so it stays open rather than closing between packets.

# equivalent AT commands
AT+SOCKAEN=ON
AT+SOCKASL=LONG
AT+SOCKA=TCP,crtk.net,2101

Build the NTRIP GET request

Write the request as plain text with \r\n line endings and a blank line at the end, then convert it to hex. A hex↔text converter is the easiest way to sanity-check it before pasting it into the device.

GET /KOLR HTTP/1.1
Host: caster.centipede.fr:2101
Ntrip-Version: Ntrip/2.0
User-Agent: NTRIP PUSR-G771
Authorization: Basic Y2VudGlwZWRlOmNlbnRpcGVkZQ==

Enable the Identity Package

This is what actually sends the GET request. Set it to fire once, as user-defined hex data, right when the socket connects.

AT+REGEN=ON
AT+REGTP=USER
AT+REGDT=<hex string from step 3>
AT+REGSND=LINK

Match the serial port to your receiver

The baud rate, parity and stop bits here need to match whatever your GNSS receiver expects on its correction input — not necessarily the modem's default.

Save, restart, and watch the log

Send AT+S to save and reboot the modem. On reconnect you're looking for an HTTP 200 / ICY 200 OK response, then a continuous stream of binary data with no repeated reconnects.

One limitation to know about: some terminals only unlock their RTK correction menu when their original OEM telematics module is physically present, since it authenticates over a separate bus before the correction source even matters. If RTCM is streaming correctly but the receiver does nothing with it, that's the next thing to check — not the NTRIP setup itself.
Bandwidth footnote: the GET request is a one-time ~300 bytes; the ongoing RTCM stream typically runs 0.5–2 MB/hour depending on constellations and update rate.
